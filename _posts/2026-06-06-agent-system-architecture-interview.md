来，我们做一个面试场景的模拟。

假如你去面试一个 AI 产品经理或者 Agent 开发工程师的岗位，面试官看了你的简历，问了一个问题：

> "看你简历写了一个 AI 客服系统，那你讲讲这个系统你是怎么做的？"

这个问题看似基础，但很多人答不好。要么照着稿子念概念，把 ReAct、Plan-and-Execute、Multi-Agent Collaboration 这些词堆一遍。要么讲出来的东西没什么含金量，一听就露馅——"我就接了个大模型，做了个 RAG，然后上线了"。


## 面试官问我这个问题，我会这么聊

我们当时做这个智能客服系统，不是简单选个模型、搭个 Prompt 和工作流就上线了。而是要在 **效果、成本、风险** 之间找一个平衡。

很多人会把 Agent 理解成"更强的 LLM"，但实际不是。面试中经常有一个问题——"Agent 和普通的 LLM 调用有什么区别？"

普通 LLM 是问一句答一句，凭训练数据里的印象回答，像一个只会背书的学生。而 Agent 是一个**有自主性的系统**，有三个核心组件：

- **规划**——拿到任务先拆解，先做什么、再做什么、要不要查资料
- **记忆**——做完的事能记住，下次不用重头再来
- **工具**——能调数据库、搜文档、执行代码，不只是动嘴

我们面临的问题，不只是选哪个模型或者工作流怎么画，而是把精力放在了四个维度上：**业务目标怎么拆、场景怎么分层、能力怎么建设、兜底机制和评估怎么做**。

整个产品，我是分这四个维度去搭的。

---

## 第一维度：先拆业务目标

我们没有一上来就搭方案。

第一步是先搞清楚：**这个业务的目标到底是什么？**

是提升客服的自助解决率？降低转人工率？缩短平均处理时长？提升客户满意度？还是降低客服成本？

目标不一样，后面的优先级、场景选择、能力建设和评估体系，全都不一样。

比如说，如果核心目标是降本，那优先做的场景应该是量最大的那些，ROI 最高。如果核心目标是提升满意度，那体验相关的"转人工无缝衔接"这类能力优先级就要往上提。

先把业务目标拆清楚，再来拆项目阶段，一步一步推进下去。

---

## 第二维度：业务场景分层

很多团队犯的错误是一口气把整个智能客服全部推上线。但智能客服要覆盖的场景太多了，不同场景需要的智能化能力不一样。

我们拆场景分了四个维度：**问题的频次、标准化程度、风险等级、商业价值**。分四个阶段来推进。

### 第一阶段：高频、标准化、低风险的问题

像物流查询、退换货规则、发票、会员权益——这类问题都有标准答案，ROI 最高，验证快，风险最低。

这个阶段的核心考验是 **知识库的搭建和检索的准确性**。不是简单接个 RAG 完事，而是要考虑几个实操问题：

**知识库的治理**——我们画了一条红线：答错比答不出来更危险。所以知识库要管好四件事：**完整性**（知识覆盖全不全）、**时效性**（有没有及时更新）、**一致性**（不同来源口径是否一致）、**可追溯**（每个回答能否溯源到原始文档）。

**权限隔离**——企业级系统里客服同学的知识和研发同学的故障记录放在同一个知识库，不能让客服搜到研发的敏感信息。不能靠 Prompt 约束（Prompt 可能被绕过）。正确做法是**在向量检索阶段做物理隔离**：文档入库时带上权限标签，检索时强制带上用户身份作为过滤器，从源头杜绝越权访问。

**内容更新快**——知识库不是静态的。产品文档天天改，Agent 检索到旧版本 embedding，给的就是过时的答案。常用策略是**动态路由**——Agent 先判断问题的时效性，高时效问题直接调实时 API 或搜索工具，不走向量库。知识库更新方面，用 **Kafka 监控变化、增量更新 embedding**，配合**缓存失效策略**保证答案不滞后。

### 第二阶段：需要查系统状态的场景

像查订单、催发货、修改地址、查收货进度——光靠知识库不够了，需要跟后端订单系统、物流系统打通。方案重点从"问答"转向**系统对接和状态流转**。

这里就涉及一个关键问题：**Agent 调工具，怎么保证不出错？**

Agent 调外部工具时经常出错——参数格式不对、字段名拼错、类型不匹配。这是 LLM 生成的不确定性带来的。我们从三层来解决：

1. **语法层**：用 Pydantic 做参数约束，生成的参数先校验再执行
2. **逻辑层**：高风险操作（如修改订单地址）引入人工确认
3. **容错层**：参数报错时，把错误信息返回给 Agent 让它自我修复重试

同时这里也要想清楚：**什么时候用工作流，什么时候让 Agent 自己发挥？**

工作流（画好的流程图）适合确定性高的场景——物流查询、退换货流程，走完了就能拿到结果，优点是稳。自主 Agent 适合开放式场景——用户说不清楚自己要什么，LLM 自己决定怎么追问、怎么调整。我们实际做的时候是**混着用的**：核心流程用工作流兜底，关键决策点交给 Agent 自由发挥。

### 第三阶段：多轮复杂场景

用户说不清楚自己要什么，Agent 需要追问、确认、给选项。这里涉及 **Agent 的对话管理和状态管理**：

- 什么时候追问、什么时候确认、什么时候给选项
- 什么时候结束、什么时候转人工

多轮对话容易踩的坑是 **状态爆炸和上下文溢出**。我们用了三个策略：

1. **State Schema**——定义严格的状态结构（类似 LangGraph 的 TypedDict），只保存核心变量
2. **摘要压缩**——长对话定期压缩成摘要，保留关键信息
3. **旧对话摘要化**——把历史对话摘要存入 Context 头部

还有一个常见面试题：**记忆是怎么工作的？短期和长期各管什么？**

短期记忆用 Context Window 存当前会话历史。长期记忆通过 **RAG** 把历史经验和知识编码为向量存入向量数据库。Agent 执行任务前先检索相关历史经验。当对话历史很长时，不会全部塞进 Context，而是先做摘要压缩，只保留关键内容。

### 第四阶段：高风险问题

像赔付、争议判定、投诉、敏感合规——这类场景在前期绝不能让 Agent 完全自动化处理，风险太高。我们采用**人机协作 + 兜底机制**，Agent 做信息收集和预处理，最终决策交给人工。

这里会遇到一些更复杂的问题：

**多条规则冲突，Agent 到底听谁的？**
- 按数据加权——根据文档的时效性和权威性做权重排序
- 多 Agent 辩论——不同 Agent 参考不同来源，对比识别冲突点
- 溯源——强制输出附带来源链接，让用户最终校验

**大表格处理**——客服场景中常有几百行的参数表，直接塞进 Context 要么超限、要么干扰推理。做法是**先摘要再选择性读取**：LLM 先通过表头和摘要判断是否包含所需数据，如果有就生成查询指令只提取对应的行和列，把子表交给模型处理。数据量小、干扰少、准确度还高。

**答案中要插图片**——退换货流程的配图、产品的展示图。早期做法是把图片数据也塞进 Context，又贵效果又差。推荐用**占位符方案**：文档预处理时把图片替换为占位符（如 `[图片:IMG001]`），约束 LLM 在回复对应位置保留它。前端渲染时解析器匹配占位符，从图片服务器拉取真实图片渲染。保证图文对应，又不浪费 Token。

**跨页图文关联**——解析文档时图片在上页末尾而相关描述在下页开头，常规分页解析会破坏关联。解决方案是**滑动窗口 + 跨页聚合**：解析时维护滑动窗口，通过布局距离计算将邻近文本块作为图片的上下文描述共同存储。

## 第三维度：能力建设

场景分层清楚了，接下来做对应的能力建设。我们重点做了四个方面。

### 1. 理解能力

用户表达不标准，"我的东西怎么还没到"和"查一下快递"是同一个意图。所以不能靠关键词匹配，而要做**意图识别和上下文理解**——知道用户当前在哪个任务节点、说了什么、想要什么。

### 2. 知识库能力

前面第一阶段已经提到了知识库治理的几个要点，这里再补充一个：**当单个 Agent 做复杂任务做着做着就跑偏了怎么办？**

比如用户问了一个跨领域问题——既涉及退换货规则又要查物流状态还要计算赔偿金额。单一 Agent 容易"注意力漂移"，做着做着就偏了，推理质量下降。

这时候需要**多 Agent 协作**，常见模式有三种：

- **中心化模式（Orchestrator）**——一个主 Agent 拆任务，分给专门子 Agent 执行，最后汇总。生产环境最常用，可控性最强。
- **流水线模式（Pipeline）**——A 做完传给 B，B 处理完给 C。比如：一个 Agent 查订单，第二个处理退款，第三个通知用户。
- **民主协作模式（Debate）**——多个 Agent 各执一词讨论出结论，适合决策场景。

多 Agent 协作有个新问题：**无限循环**。Agent 之间聊起来没完没了。解决方式很实在——用有限状态机控制流程、设最大迭代次数、定期摘要压缩 Agent 间对话、事先定义好完成标准。

如果用的是中心化模式，还有一个经验：**最难的不是把任务分下去，而是怎么拆**。拆太细 Worker 之间通信开销大、系统变慢；拆太粗每个 Worker 任务还是太重、照样出幻觉。原则是**单一职责**——每个 Worker 只做自己领域内的事，粒度控制到 1-2 次 LLM 调用内能完成的水平。

### 3. 执行能力

光会聊天不会干活，价值有限。我们推动系统跟订单、物流、售后工单、CRM 打通，让 Agent 具备从**查询到调用、到触发、到记录**的完整链路能力。

这个环节要回答另一个面试常问题：**Orchestrator-Worker 模式里，怎么保证 Worker 的执行质量？**

关键就是前面说的——工具调用的可靠性（三层兜底）、单一职责的拆分、以及明确的成功标准定义。

### 4. 记忆能力

前面已经讲了短期记忆和长期记忆的分层。再补充一点：我们还会记录每个用户的服务轨迹，包括历史对话摘要、已解决/未解决的问题清单、用户的偏好信息。这些数据既用于提升回答的个性化程度，也用于提升转人工时的交接效率。

## 第四维度：兜底机制和效果评估

没有兜底机制，系统上线就很容易失控。

### 兜底策略

我们设计了一套系统性的兜底机制和触发条件：

- **低置信度**：Agent 不确定答案时退回标准 FAQ 或转人工
- **规则冲突**：保守回答 + 标记给人工审核
- **工具调用失败**：重试 → 降级 → 转人工，三级回退
- **多轮未解决**：几轮对话后仍未解决用户问题，判断转人工时机
- **高风险问题**：涉及资产损失、投诉、合规，直接进入人工协助

其中**人工协助**这个点花了很多精力。不是说转人工就撒手不管了——转人工之前，需要把用户意图、历史对话、已确认信息、调用了哪些知识、执行了哪些动作、当前卡在什么地方，全部结构化地整理给人工。这样人工接手时不是从零开始，服务链路才不断。

### 效果评估

面试中还有一个高频问题：**你怎么量化 Agent 干得好不好？**

不能只盯一个指标。我们分了四个层面：

**第一层——业务指标：**
自助解决率、转人工率、平均处理时长、单问题处理成本

**第二层——能力质量指标：**
回答正确率、任务完成率、知识命中率、意图识别准确率

**第三层——风险指标：**
幻觉率、错误承诺率、高风险问题暴露率

**第四层——系统指标：**
工具调用成功率、响应时长、人工转接成功率

上线新策略前我们做**灰度测试**——线上并行跑新旧两套逻辑，对比输出差异。差异大说明新方案不稳定，继续优化再推全。

---

整个项目前前后后花了多少时间、迭代了多少个版本、最终某项数据从多少提升到了多少——你把这些数据一摆，面试官一听就知道你是有水平的。

因为整个讲述思路非常清晰——怎么从业务目标开始拆解、怎么把场景分阶段推进、每个阶段对应的能力怎么建设、出了问题的兜底机制是什么、最终怎么评估效果。有条理、有层次、有逻辑。

你这么来聊，才会让面试官觉得：你不光做过，而且真的有专业度，真正有水平。

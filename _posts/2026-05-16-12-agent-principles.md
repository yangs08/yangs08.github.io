很多朋友第一次听到 AI Agent，会下意识觉得这东西很神秘。

好像模型突然有了自主意识，会自己思考，会自己调用工具，会自己拆任务，还能带着一群小模型一起干活。

其实真拆开看，没有那么玄。

Agent 不是一个神秘的新物种，它更像一套工程组合拳，一边让大模型输出文字，一边让外部程序读懂这些文字，再去执行工具、检索资料、保存状态、继续追问。

也就是说，大模型负责「想和说」，程序负责「记和做」。

这篇文章我想用尽量大白话的方式，把 12 个 Agent 底层原理讲清楚。你不需要先懂论文，也不需要先会写框架。只要你用过 ChatGPT、Claude 或者 Codex，大概都能顺着看下来。

先放一个最小心智模型。

## 1. Messages 数组，AI 看到世界的唯一入口

你跟大模型聊天，表面上看是一个对话框。

但在接口层面，它看到的通常不是一个对话框，而是一个 `messages` 数组。

你可以把这个数组想象成一叠聊天记录。第一张纸写着系统要求，第二张纸写着你刚才说了什么，第三张纸写着模型之前回了什么。模型每次回答前，都会把这叠纸从头到尾读一遍，然后接着往下写。

一个最简单的请求长这样。

```json
[
  { "role": "system", "content": "你是一个耐心的编程老师" },
  { "role": "user", "content": "用大白话解释一下什么是 Agent" }
]
```

这就是最底层的对话通道。

所以你要记住第一件事，AI 不是直接「看见」你的应用、文件、按钮和数据库。它先看见的是你塞进 `messages` 里的文字。

Agent 后面所有复杂能力，都是从这个数组开始长出来的。

## 2. 上下文窗口，AI 的记忆其实是重放

很多人会问，AI 到底有没有记忆？

坦率地讲，大多数时候它不是像人一样在脑子里存了一段回忆。

它所谓的记住，是你每次请求时，把前面的聊天记录又发给它了。

比如第一轮你说，我在做一个 Jekyll 博客。

第二轮你问，刚才那个博客怎么改首页？

模型之所以知道「刚才那个博客」，不是因为它真的在某个脑区里存着这件事，而是程序把第一轮对话也放回 `messages` 里了。

这块有个关键词叫上下文窗口。

上下文窗口就是模型一次能读进去的文字容量。窗口越大，你能塞进去的历史、文档、代码就越多。窗口不够了，就得截断、总结、检索，或者让程序帮它挑重点。

Agent 的记忆系统，本质就是围绕这个限制做工程。

短期记忆靠上下文重放，长期记忆靠外部存储，真正回答时再把相关内容捞回来。

## 3. System Prompt，给 AI 一套行为规则

`system prompt` 可以理解成写在最前面的说明书。

用户说的话很重要，但系统提示词通常更像「这次任务的角色和规矩」。

比如你写。

```
你是一个耐心的编程老师。解释概念时先给类比，再给代码例子。
```

同样一个问题，如果系统提示词不同，模型的回答方式会完全不一样。

你让它当老师，它会解释得慢一点。你让它当代码审查员，它会优先挑 bug。你让它当翻译器，它就会少废话，直接翻译。

很多 Agent 框架都会有一大段系统提示词，里面写着工具怎么用、输出格式是什么、遇到错误怎么办、什么时候停止。

这不是装饰。

这是 Agent 的说明书。

说明书写得清楚，Agent 就稳一点。说明书写得含糊，Agent 就容易乱来。

## 4. 思维链，让模型先铺路再回答

大模型有个很有意思的地方。

你直接问它一个复杂问题，它可能会给你一个看起来很自信、其实算错了的答案。

但你让它先拆步骤，它往往会更稳。

这就是大家常说的 Chain of Thought，思维链。

当然，现在很多模型和产品不会把完整思考过程展示给用户，但工程思路还是一样的，复杂任务不要指望模型一步跳到答案，要让它先整理条件、拆解问题、检查约束，再输出结果。

举个简单例子。

你问它，一个功能为什么报错？

差一点的提示是，帮我修 bug。

更好的提示是，先列出可能原因，再根据日志排除，最后给出最小修改方案。

这就像你做数学题，直接写答案容易蒙，先写草稿更容易发现哪里错了。

Agent 做任务也一样。

它需要计划，需要观察，需要修正，不然就是一路往前冲。

## 5. Few-Shot，给例子比讲道理管用

有时候你会发现，跟 AI 说十遍格式要求，它还是输出得乱七八糟。

这时候别急着骂它。

直接给例子。

比如你希望它把用户输入解析成固定 JSON，光说「请输出 JSON」不一定稳。你给它两个样例，它立刻就明白了。

```
输入，帮我查北京天气
输出，{"tool":"weather","city":"北京"}

输入，帮我总结这篇文章
输出，{"tool":"summarize","target":"article"}
```

这就叫 Few-Shot，多样本提示。

它特别适合 Agent。

因为 Agent 经常要让模型输出结构化内容。工具名是什么，参数是什么，下一步动作是什么，都不能太随缘。

你给它例子，相当于把路标插在地上。

模型不一定真的理解你所有抽象规则，但它很擅长模仿例子的形状。

## 6. 预填充，帮模型把开头写死

有时候模型最大的问题不是不会，而是太爱客套。

你想要 JSON，它先来一句，好的，下面是你需要的结果。

对普通聊天来说无所谓，对程序来说就麻烦了。因为程序要解析 JSON，多出来一句话，解析器可能直接炸掉。

预填充就是一个很朴素的办法。

你不让模型从空白处开始写，而是先替它写好开头。

```json
{
```

模型看到开头已经是 `{`，就更容易顺着写 JSON，而不是先寒暄。

很多工程细节都是这种感觉。

不是靠一句神奇咒语让模型突然变聪明，而是把它容易跑偏的空间一点点收窄。

## 7. 停止序列，让模型在该停的地方停

Agent 经常会出现一个问题，模型不只想说下一步动作，它还想把动作结果也编出来。

比如你让它输出。

```
Action，search
Action Input，今天北京天气
Observation，
```

如果不拦住它，它可能会接着写，Observation，北京今天晴。

问题是，它根本还没查天气。

这就是幻觉从聊天进入工程系统的瞬间。

停止序列就是告诉生成器，写到某个标记就停下来，把控制权交回程序。

程序拿到 Action，真的去调用搜索工具。工具返回结果以后，再把 Observation 塞回上下文。

这样模型负责决定要做什么，程序负责确认发生了什么。

这个边界非常重要。

## 8. Tool Use，AI 不是自己点工具

这块是很多人最容易误解的地方。

AI 真的会调用工具吗？

严格讲，大模型本身不会。

它只会输出文字。

所谓工具调用，是外部程序和模型约定好一种格式。

模型输出。

```json
{
  "tool": "weather",
  "arguments": {
    "city": "北京"
  }
}
```

程序看到这段 JSON，才真的去调用天气 API。

调用完以后，程序再把结果发回给模型。

所以 Tool Use 的本质不是模型长出了手，而是我们给模型装了一个「说暗号就能触发动作」的外壳。

暗号说对了，程序执行。

暗号说错了，程序拒绝。

这就是工具调用最朴素的底层逻辑。

## 9. RAG，让 AI 现查现答

大模型并不天然知道你的公司文档、项目代码、内部 SOP。

你问它一个内部问题，它如果没资料，只能根据训练里的通用知识猜。

RAG 做的事很直白。

先检索，再回答。

用户问问题以后，程序先去知识库里找相关文档，把最相关的几段塞进上下文，再让模型基于这些内容回答。

它不是突然懂了你们公司。

它是开卷考试。

这也是为什么 RAG 工程里，检索质量特别重要。你塞进去的资料不对，模型再会写也没用。它会围着错误资料讲得头头是道。

我自己的感受是，RAG 最容易被低估的地方，不是生成，而是前面的资料选择。

找得到，排得准，截得合适，模型才有机会答好。

## 10. ReAct，让 Agent 一边想一边做

ReAct 是 Reasoning and Acting 的缩写。

听起来挺学术，其实很好理解。

它就是让模型在一个循环里反复做三件事。

想一下。

动一下。

看结果。

比如用户问，帮我查一下某个项目最近的发布说明。

Agent 可能先想，我需要去 GitHub。

然后动作是调用搜索或 GitHub 工具。

工具返回结果以后，它再观察，发现找到了 release 页面。

接着它继续想，我需要总结最新版本变化。

这就是 ReAct。

如果你写成程序，大概就是一个 `while` 循环。模型每轮输出下一步，程序执行工具，把结果塞回去，再进入下一轮。

所以 Agent 看起来像在自主决策，底层其实是模型输出和程序执行轮流接力。

## 11. 自回归生成，为什么 AI 会一本正经地编

大模型生成文字的方式，可以简单理解成根据前面的内容，预测下一个最可能出现的词。

它不是先在脑子里查一张事实表，再把答案抄出来。

它是在不断续写。

这也是为什么它有时候会一本正经地编。

你问一个它不知道的问题，如果没有工具、没有资料、没有约束，它也可能给你续出一段很像答案的文字。

这不是它故意骗人，而是生成机制就长这样。

所以做 Agent 的时候，不能只相信模型嘴上说了什么。

要让它引用依据，要让工具返回事实，要让程序校验格式，要在关键步骤留出检查。

AI 很会说。

工程系统要负责让它说得有边界。

## 12. Multi-Agent，不是一群 AI 开会那么简单

Multi-Agent 听起来很酷，好像一群 AI 坐在会议室里各司其职。

但真落到工程里，核心问题不是多叫几个模型。

核心问题是怎么分工，怎么传递上下文，怎么合并结果，怎么避免互相甩锅。

比如做一个旅行规划，你可以拆成几个角色。

一个查交通。

一个查酒店。

一个排行程。

一个做预算。

最后再由一个主 Agent 汇总。

这确实有用，因为复杂任务被拆小了，每个 Agent 的上下文更聚焦。

但它也会带来新麻烦。中间信息可能丢，多个 Agent 的结论可能冲突，成本和延迟也会上去。

所以 Multi-Agent 不是越多越好。

一个 Agent 能解决的问题，就别硬开一桌会。只有当任务真的需要拆分、并行、交叉检查时，多 Agent 才有意义。

说到最后，其实 Agent 没那么神秘。

它不是一个单点技术，而是一组很朴素的工程方法拼起来。

`messages` 负责把话送进去。

上下文窗口负责让模型看见历史。

system prompt 负责定规则。

思维链负责拆问题。

Few-Shot 和预填充负责稳格式。

停止序列负责交还控制权。

Tool Use 负责把文字变成动作。

RAG 负责把资料临时搬进考场。

ReAct 负责循环推进。

自回归生成提醒我们，模型会编，所以必须校验。

Multi-Agent 则是在任务变大以后，把问题拆给多个角色。

看起来很多。

但你只要抓住一句话就够了。

Agent 的本质，是让大模型在程序搭好的轨道里，一步一步完成任务。

模型不是万能大脑。

它更像一个很会读写、很会推理、但需要工程护栏的执行伙伴。

把护栏搭好，Agent 才真的能干活。

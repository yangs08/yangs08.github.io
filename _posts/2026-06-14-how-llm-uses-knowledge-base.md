大模型接知识库，不能只理解成「文档切块、向量检索、塞进 prompt」。

真正做的时候，第一步要先想清楚两件事：

```text
数据从哪里来？
数据要整理成什么结构？
```

如果这两件事没做好，后面不管用 RAG、GraphRAG，还是 Agentic RAG，效果都会不稳定。

因为大模型不是直接理解业务。

它只能使用你整理好、检索出来、放进上下文里的知识。

整体链路大概是这样：

![大模型使用知识库的 RAG 链路](/images/posts/llm-knowledge-base-rag.png)

这张图里有两件事要分开看。

第一，离线阶段要把原始资料变成可检索的数据，也就是 `Documents → Chunking → Vector Database`。

第二，在线阶段不是让大模型直接读数据库，而是先根据用户问题检索相关上下文，再把 `Query + Relevant Contexts` 拼进 prompt，让大模型生成回答。

这篇主要讲图里的上半部分：怎么把原始资料变成可检索、可引用的数据。

至于在线阶段怎么检索、怎么重排、怎么补上下文，可以单独再写。

所以知识库建设的第一步，不是选工具，而是先把业务知识整理成模型能用的数据。

## 一、数据从哪里来

知识库一定来自业务场景。

先不要急着问用什么向量数据库，而是先问：

```text
用户会怎么问？
客服平时怎么答？
规则写在哪里？
历史问题怎么处理？
哪些内容经常变化？
哪些内容风险最高？
```

以电商客服为例，知识来源通常不是单一的。

它可能来自平台规则、客服经验，也可能来自视频课程、直播培训、录音访谈这类非结构化内容。

![知识库数据来源](/images/posts/knowledge-base-sources-table.png)

这几类数据的处理方式不一样。

平台规则权威，但通常很长、很书面化，所以入库前要拆分、加版本号、加平台字段。

客服经验贴近真实问题，但表达不够规范，所以要清洗、总结，并保留来源。

视频课程、录音访谈这类非结构化内容信息量大，但不能直接检索，需要先转文字、切段，再提炼成知识点。

所以知识库建设的第一步，不是 embedding。

而是先把不同来源的业务知识，整理成适合检索和引用的结构。

## 二、原始资料不能直接入库

很多知识库效果不好，不是因为模型不行，而是因为原始资料太乱。

比如平台规则原文可能是：

```text
消费者自签收商品之日起七日内，有权依法申请无理由退货，但特殊商品除外。
```

这句话是对的，但用户不会这么问。

用户会问：

```text
我收到货 3 天了还能退吗？
拆了包装还能退吗？
不喜欢可以退吗？
```

如果知识库里只有平台原文，用户口语化一问，向量检索未必稳定命中。

所以在电商客服这种场景里，我更倾向于把知识整理成：

```text
question + content
```

`question` 表示用户可能怎么问。

`content` 表示真正要给大模型参考的知识。

比如：

```json
{
  "question": [
    "收到货几天内可以退？",
    "七天无理由退货怎么算？",
    "拆封了还能退吗？",
    "不喜欢商品可以退吗？"
  ],
  "content": "消费者自签收商品之日起七日内，可以依法申请无理由退货；但特殊商品、定制商品、拆封后影响二次销售的商品除外。"
}
```

用户真实提问时，先和 `question` 做语义匹配。

命中以后，再把对应的 `content` 给大模型参考。

也就是说：

```text
question 负责提高召回
content 负责提供答案依据
```

## 三、content 放什么

`content` 可以有两种来源。

一种是原文。

比如平台规则、官方说明、合同条款。

这类内容权威，适合保留原始表达。

另一种是整理后的内容。

比如微信群讨论、客服经验、视频课程。

这些内容原始形态很散，可以先让大模型整理成更适合客服使用的知识。

比如原始内容是：

```text
这个情况一般不要直接答应退款，要先看物流是不是揽收了。如果揽收后一直没动，可以先建异常件工单。用户情绪比较激动的话，先说帮他核查，不要说一定能退。
```

可以整理成：

```json
{
  "question": [
    "物流揽收后一直不动怎么办？",
    "订单发货后没物流更新能退款吗？",
    "用户因为物流停滞要求退款怎么处理？"
  ],
  "content": "如果订单已揽收但物流长时间未更新，应先创建物流异常工单核查；在核查结果出来前，不要直接承诺退款。用户情绪激动时，先说明会协助核查，并告知后续可能根据物流结果处理退款或补发。"
}
```

这里要注意，整理不等于丢掉来源。

每条知识最好保留：

```json
{
  "source": "客服微信群总结",
  "updated_at": "2026-06-14"
}
```

否则后面出了问题，很难追溯这条知识是从哪来的。

## 四、字段设计要服务业务过滤

刚开始可以只有：

```text
question
content
```

但业务复杂以后，一定要加元数据。

这里的 metadata 可以理解成一条知识的「身份证」和「使用说明」。

`content` 负责告诉大模型这条知识说了什么。

`metadata` 负责告诉系统这条知识应该在什么情况下被使用。

比如电商客服场景里，可以这样设计：

| 字段 | 含义 | 例子 | 作用 |
| --- | --- | --- | --- |
| `category` | 业务分类 | 退款、物流、发票、投诉 | 限定问题所属场景 |
| `platform` | 适用平台 | 淘宝、拼多多、抖音 | 避免跨平台召回错误规则 |
| `version` | 规则版本 | `2026-06` | 避免旧规则继续生效 |
| `source` | 知识来源 | 平台规则、客服总结、微信群 | 判断可信度，方便追溯 |
| `updated_at` | 更新时间 | `2026-06-14` | 判断内容是否过期 |
| `priority` | 优先级 | 官方规则高于群聊经验 | 多条知识冲突时决定听谁的 |
| `risk_level` | 风险等级 | low / medium / high | 高风险问题触发人工或更严格兜底 |

没有 metadata，检索只能看「像不像」。

有了 metadata，系统才能先过滤出「该不该用」。

比如：

```text
用户问拼多多规则，就不能召回淘宝规则。

用户问最新赔付政策，就不能拿旧版本。

用户问投诉升级，就要优先召回高权威来源。

高风险赔付问题，不能只靠相似度决定答案。
```

所以字段设计其实是在回答：

```text
检索时怎么过滤？
冲突时听谁的？
旧内容怎么排除？
高风险内容怎么兜底？
```

只做向量相似度，不做元数据过滤，知识库很容易乱。

## 五、简单场景和复杂场景，知识库形态不同

电商客服这种场景，很多知识可以整理成问答卡片。

```text
question + content + metadata
```

因为问题相对短，答案相对标准，业务边界比较清楚。

但研究型场景不一样。

比如让 Agent 分析一个行业、一家公司、一个产品。

知识来源可能是：

```text
研报
访谈
新闻
论文
财报
产品文档
长篇文章
```

这些文本很长，不能简单整理成一条问答。

通常要拆成 chunk。

但 chunk 会带来一个问题：

**命中一段，不代表知识完整。**

比如用户问：

```text
这家公司为什么从工具产品转向平台型产品？
```

向量检索可能只召回一段：

```text
2024 年，公司开始开放 API，并推出开发者生态。
```

这段相关，但不完整。

完整答案可能还需要：

```text
之前的收入瓶颈
用户群变化
竞品压力
组织调整
商业模式变化
管理层表态
```

所以研究型知识库不能只考虑 chunk。

还要考虑这段内容在原始资料里的位置，以及它和其他知识的关系。

```text
这个 chunk 属于哪篇文档？
属于哪个章节？
前后文是什么？
关联哪些公司、产品、人物、事件？
和其他资料有什么关系？
```

这时候知识结构可能变成：

| 结构 | 是什么 | 例子 | 解决什么问题 |
| --- | --- | --- | --- |
| `document` | 原始文档 | 一篇研报、一份财报、一篇访谈稿、一份产品文档 | 这条知识从哪份完整资料里来？ |
| `section` | 文档里的章节 | 商业模式、用户增长、竞争格局、退款流程 | 这条知识属于哪个主题段落？ |
| `chunk` | 被切出来、参与向量检索的小片段 | 文档中的一段话、一个小节里的几句话 | 用户问题最先命中了哪段文本？ |
| `entity` | 文本里出现的重要对象 | 公司、产品、人物、平台、政策、事件 | 这段知识提到了哪些关键对象？ |
| `relation` | 这些对象之间的关系 | 公司 A 推出了产品 B；产品 B 面向开发者；政策 C 影响退款流程 | 这些对象之间怎么连接？ |

普通 RAG 往往只关心 `chunk`。

复杂场景里，`chunk` 只是入口。

真正有价值的是顺着这个入口，找到它所在的 `document`、`section`，以及相关的 `entity` 和 `relation`。

## 六、什么时候需要 GraphRAG

普通 RAG 更像是在文档里找相似片段。

它适合标准问答。

比如：

```text
退货政策是什么？
物流异常怎么处理？
发票怎么开？
```

但复杂研究问题，往往不是找到一段话就能回答。

它需要把多个事实连起来。

比如：

```text
某公司战略变化
关联 产品线变化
关联 用户群变化
关联 收入结构变化
关联 竞品动作
关联 管理层表态
```

这时候知识不是一条条孤立文本，而是一张关系网。

GraphRAG 要解决的就是这个问题。

它不只存文本，还会提取实体和关系，让系统能从命中的片段继续扩展上下文。

![GraphRAG 从片段扩展到关系上下文](/images/posts/graphrag-expanded-context.png)

这里要注意，GraphRAG 不是「把命中片段的前后文一起带上」这么简单。

如果只是命中第 3 段以后，把第 2 段、第 4 段也带上，那叫上下文扩展。

GraphRAG 更进一步，它关心的是实体和关系。

普通 RAG 通常是：

```text
问题
  ↓
命中几个相似 chunk
  ↓
把 chunk 给大模型
```

GraphRAG 会多做一步：

```text
先命中 chunk
  ↓
找到它所在的 section 和 document
  ↓
找到它提到的 entity
  ↓
沿着 relation 找到相关事实
  ↓
把扩展后的上下文给大模型
```

也就是说，它不是只问「哪段文本最像」。

它还会问：

```text
这段文本属于哪里？
它提到了谁？
这些对象之间有什么关系？
还有哪些相关事实应该一起看？
```

```text
公司 A → 推出 → 产品 B
产品 B → 面向 → 开发者
公司 A → 收入压力来自 → 企业客户增长放缓
竞品 C → 发布 → 类似平台能力
```

当用户问复杂问题时，系统不仅检索相似文本，还能沿着关系找到相关知识。

GraphRAG 适合：

```text
研究分析
复杂归因
多文档综合
实体关系密集
需要跨材料推理
```

但如果只是电商客服问答，上来就做 GraphRAG，通常是过度设计。

## 写在最后

这篇的核心是：

```text
知识从哪里来？
原始知识怎么清洗？
用户会怎么问？
content 怎么写？
metadata 怎么设计？
不同场景要不要不同结构？
```

电商客服这种标准场景，可以从 `question + content + metadata` 开始。

研究分析这种复杂场景，要考虑 `document + section + chunk + entity + relation`。

所以这篇先不讲怎么查。

在查之前，先把数据整理成值得被查、也能被正确使用的样子。

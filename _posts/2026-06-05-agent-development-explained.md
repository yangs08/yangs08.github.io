这两年 Agent 开发是技术圈最火的方向之一，面试中相关的问题也越来越多。但很多人在准备时容易陷入一个误区——背概念。背了一堆"ReAct"、"Plan-and-Execute"、"Multi-Agent Collaboration"，面试时被追问一句"具体怎么落地"就卡住了。

这篇文章把 Agent 开发中常见的核心问题串起来，不讲大词，就说清楚每个问题背后的为什么，以及实际中是怎么解决的。

## 一、Agent 到底是什么？和普通 LLM 调用有什么区别？

很多人刚开始接触时觉得：Agent 不就是调大模型接口吗？

其实差别很大。普通 LLM 调用是"问一句答一句"，模型凭训练数据里的印象回答。而 Agent 更像一个**有自主性的系统**，它有三个核心组件：

- **规划**：拿到任务后先拆解——先做什么、再做什么、要不要查资料
- **记忆**：做完的事能记住，下次不用重头再来
- **工具**：能调数据库、搜文档、执行代码，不只是"动嘴"

打个比方：普通 LLM 像一个只会背书的学生，你问什么他凭记忆答什么。Agent 则像一个会查资料的研究员——拿到问题先规划步骤，翻书确认事实，把结论记下来，下次遇到类似问题直接调经验。

这也是为什么面试时经常会问"Agent 的基本架构组成"——其实就是在看你是不是真的理解这三层。

## 二、记忆是怎么工作的？短期和长期各管什么

Agent 有记忆，但不能无限记。所以需要把记忆拆成两层来管：

**短期记忆**就是当前会话的上下文。比如你和 Agent 连续聊了五轮对话，它记得你刚才说了什么。实现上就是用 LLM 的 Context Window 来存。

**长期记忆**是跨会话的。比如 Agent 昨天帮你查了一个产品的版本信息，今天你问另一个问题时，它应该能调取昨天的经验，而不是每次都从头搜。实现方式通常是 RAG——把历史经验和知识编码成向量存到向量数据库里，需要时检索回来。

这里有个常见优化点：当对话历史很长时，不会全部塞进 Context（太贵也太容易超限），而是先做**摘要压缩**，只保留关键内容。

现在还有一种趋势是利用**长上下文模型**直接处理整段历史，但这更多是硬件层面的进步，架构设计上还是推荐分层管理。

## 三、一个人干不了的时候，怎么上多 Agent 协作

单个 Agent 不是万能的。遇到**跨领域的复杂任务**，比如既要理解技术文档又要做数据分析还要输出报告，单一 Agent 很容易"注意力漂移"——做着做着就偏了，推理质量明显下降。

解决思路是让多个 Agent 分工协作，常见的模式有三种：

**第一种：中心化模式（Orchestrator）**
一个主 Agent 负责拆任务，分给几个专门的子 Agent 执行，最后汇总结果。这是生产环境最常用的模式，可控性最强。

**第二种：流水线模式（Pipeline）**
A Agent 做完把结果传给 B，B 处理完再给 C。比如代码审查场景：一个 Agent 写代码，第二个审核，第三个修复问题。一环扣一环。

**第三种：民主协作模式（Debate）**
多个 Agent 各执一词，讨论出结论。适合决策类场景——比如判断某个方案是否可行，不同 Agent 从不同角度分析，最后达成一致。

多 Agent 协作有个新问题：**无限循环**。Agent 之间聊起来没完没了。解决方式也很实在——用有限状态机控制流程、设最大迭代次数、给 Agent 之间的对话做定期摘要压缩、事先定义好"什么状态算完成"。

## 四、什么时候用工作流，什么时候让 Agent 自己发挥

这是实践中经常要做的选择。

**工作流**（说白了就是画好的一张流程图）适合确定性高的场景。比如报销审批、标准化客服——流程是固定的走完了就能拿到结果。优点是稳，缺点是不够灵活。

**自主 Agent**适合开放式场景。比如写代码、做研究——LLM 自己决定下一步做什么、调什么工具、怎么调整。优点是灵活，缺点是结果不稳定。

实际项目中通常是**混着用的**：核心流程用工作流兜底，关键决策点交给 Agent 自由发挥。

## 五、Orchestrator-Worker 模式里，最难的其实是"拆"

这种模式下，最难的不是把任务分下去，而是**怎么拆**。

拆太细，Worker 之间通信开销巨大，整个系统变慢。拆太粗，每个 Worker 任务还是太重，仍然会出幻觉。

实践中总结的原则是**"单一职责"**——每个 Worker 只做自己领域内的事。比如一个写前端、一个写后端、一个做测试。粒度控制到每个 Worker 在 1-2 次 LLM 调用内能完成的水平。

## 六、Agent 调工具，怎么保证不出错

Agent 调外部工具时经常出错——参数格式不对、字段名拼错、类型不匹配。这是 LLM 生成的不确定性带来的。

解决思路分三层：

1. **语法层**：用 Pydantic 做参数约束，LLM 生成的参数先校验再执行
2. **逻辑层**：高风险操作（如扣款、删除数据）引入人工确认
3. **容错层**：参数报错时，把错误信息返回给 LLM 让它自己修复重试

## 七、怎么量化 Agent 干得好不好

没有指标就没法持续改进。我们关注三个核心维度：

- **任务成功率**——这是根本，一次对话下来是否达到了预期目标
- **Token 消耗和延迟**——直接影响成本和用户体验
- **工具调用正确率**——参数格式、工具选择是否正确

上线新策略前建议做**灰度测试**：线上并行跑新旧两套逻辑，对比输出差异。如果差异大说明新方案不稳定，继续优化再推全。

## 八、知识库的四个实操问题

企业级 Agent 系统绕不开知识库，而知识库一落地就有四个绕不开的问题。

### 问题 1：权限隔离

多部门的知识放在同一套系统里，不能让 A 部门的人看到 B 部门的敏感信息。不能靠 Prompt 约束——Prompt 可能被绕过的。

正确做法是**在向量检索阶段做物理隔离**：文档入库时带上权限标签，检索时强制带上用户身份作为过滤器，从源头杜绝越权访问。

### 问题 2：内容更新快

知识库不是静态的。产品文档天天改、故障记录实时产生。Agent 检索到过时的 embedding，给的就是过时的答案。

常用策略是**动态路由**：Agent 先判断问题的时效性。高时效问题直接调实时 API 或搜索工具，不走向量库。知识库更新方面，用 Kafka 监控变化、增量更新 embedding，配合缓存失效策略保证答案不滞后。

### 问题 3：答案中插图片

技术文档的回答经常需要配图。早期做法是把图片数据也塞进 Context，又贵效果又差。

推荐的方案是**占位符方案**：文档预处理时把图片替换为占位符（如 `[图片:IMG001]` ），约束 LLM 在回复对应位置保留它。前端渲染时解析器匹配占位符，从图片服务器拉取真实图片渲染。保证图文对应，又不浪费 Token。

### 问题 4：大表格处理

几百行几十列的参数表直接塞进 Context，要么超限、要么干扰推理。

做法是**先摘要再选择性读取**：不把整个表扔给 LLM，而是先通过表头和摘要判断是否包含所需数据。如果有，生成查询指令只提取对应的行和列，把子表交给模型处理。这样数据量小、干扰少、准确度还高。

## 九、多页文档中，图片和文字跨页了怎么办

解析文档时，图片可能出现在上一页末尾，而相关描述在下一页开头。常规分页解析会破坏这种关联。

解决方案是**滑动窗口 + 跨页聚合**：解析时维护一个滑动窗口，通过布局距离计算将邻近的文本块作为图片的上下文描述共同存储。这样检索时图文仍然关联在一起。

## 写在最后

Agent 开发看起来门槛很低——调个 API 就是 Agent。但真要上线跑起来，记忆怎么分治、多 Agent 怎么协作、工具调用怎么兜底、知识库怎么隔离——每个问题背后都是系统工程。

准备面试也好，做项目也好，**比起背概念，更关键的是理解每个设计背后的为什么**。知道什么时候该用什么方案、有什么代价和取舍，这些才是能拉开差距的地方。
